Guía de Arquitectura Completa para una Aplicación de Estadísticas de Balonmano con Python y JavaScript
Este informe presenta una guía arquitectónica exhaustiva para el desarrollo de una aplicación web destinada a la anotación y análisis de estadísticas de partidos de balonmano. El proyecto está diseñado para ejecutarse inicialmente en un servidor local, con una estructura robusta que facilita su futura expansión y despliegue. El enfoque combina tecnologías de frontend (HTML, CSS, JavaScript) con un backend en Python, proporcionando un plan de trabajo detallado desde el modelo de datos hasta la implementación de la comunicación cliente-servidor.
Sección 1: Definiendo el Juego — El Modelo de Datos de Estadísticas de Balonmano
La base de cualquier aplicación de datos es un modelo bien estructurado. En esta sección, se traducirán las acciones de un partido de balonmano a un formato digital. El diseño se centrará en un modelo basado en eventos, que ofrece una flexibilidad superior para el seguimiento en tiempo real y el análisis posterior.
1.1. Identificación de Categorías Estadísticas Clave
El primer paso es definir qué datos se van a registrar. Las métricas del balonmano abarcan desde contribuciones individuales básicas hasta coeficientes de rendimiento avanzados utilizados en análisis técnicos.1 Para garantizar la exhaustividad, el modelo también se inspira en la estructura de las planillas de juego oficiales.3
Los datos a registrar incluyen:
Metadatos del Partido: Nombres de los equipos, lista de jugadores por equipo, fecha del partido y duración del juego, que varía según la categoría de edad de los jugadores (por ejemplo, 2 tiempos de 30 minutos para mayores de 16 años).3
Estadísticas de Jugadores de Campo: Goles totales, lanzamientos de 7 metros (anotados y fallados), asistencias, exclusiones de 2 minutos y descalificaciones.1
Estadísticas de Porteros: Paradas totales, desglosadas por la situación del lanzamiento (desde 6 metros, 9 metros, 7 metros o contraataque).2
Estadísticas de Equipo: Posesiones totales, total de lanzamientos y goles recibidos. Estos datos son fundamentales para calcular métricas de eficacia avanzadas.2
1.2. La Arquitectura Basada en Eventos: Por Qué Registrar Acciones es Superior a Contar Estadísticas
Una decisión arquitectónica fundamental es adoptar un modelo de datos basado en eventos en lugar de un sistema de contadores agregados. Un enfoque de contadores, donde la interfaz de usuario simplemente tiene botones para "+1 Gol" o "+1 Parada", es insuficiente para un análisis profundo. Por ejemplo, para calcular una estadística crucial como el porcentaje de acierto en tiros (% Tiros), es necesario conocer tanto los goles (éxitos) como el total de intentos.1 De manera similar, los coeficientes de eficacia ofensiva y defensiva dependen del número de posesiones y lanzamientos totales, no solo de los goles marcados o recibidos.2
Una interfaz de usuario diseñada para un partido de ritmo rápido no puede permitirse tener docenas de contadores para cada posible estadística. La solución es registrar eventos discretos. La interfaz tendrá botones para acciones como "Lanzamiento desde 6m", "Pérdida de balón" o "Falta en ataque". El sistema registrará el evento y su resultado (por ejemplo, 'gol', 'parada', 'fuera').
Este enfoque desacopla la captura de datos del análisis. Durante el partido, el operador se centra en registrar acciones simples. Una vez finalizado el encuentro, el sistema puede consultar este registro de eventos para calcular cualquier estadística agregada, sin importar su complejidad. Esta arquitectura es inherentemente escalable; si en el futuro se desea analizar una nueva métrica, como "goles de contraataque por jugador", esta se puede derivar del registro de eventos existente sin necesidad de modificar el mecanismo de captura de datos.

Sección 2: Construyendo la Cabina — El Panel de Control Interactivo del Frontend
Esta sección detalla la creación de la interfaz de usuario (UI) con HTML, CSS y JavaScript. El objetivo es desarrollar un panel de control responsivo e intuitivo, optimizado para la anotación rápida de eventos durante un partido en vivo.
2.1. Estructura de la Interfaz (HTML)
El HTML semántico organizará los componentes principales de la aplicación. Se pueden encontrar tutoriales generales sobre la creación de interfaces interactivas que sirven de inspiración.5

Marcador (#scoreboard): Mostrará los nombres de los equipos, el marcador actual y el cronómetro del partido.

2.2. Estilo para la Usabilidad (CSS)
El CSS se centrará en la claridad y la capacidad de respuesta, utilizando Flexbox o Grid para un diseño adaptable. Las claves visuales son fundamentales:
Jugador Activo: Un estilo distintivo (p. ej., un borde o color de fondo) para el jugador actualmente seleccionado.
Retroalimentación de Interacción: Efectos visuales sutiles en los botones al hacer clic para confirmar la acción.

2.3. Dando Vida a la Interfaz (JavaScript)
El núcleo del frontend reside en el JavaScript, que se organizará en módulos funcionales.
El Cronómetro del Partido
Se implementará un cronómetro funcional con controles de inicio, parada y reinicio. El uso de setInterval es clave para actualizar la pantalla cada segundo.7 A diferencia de una cuenta regresiva, este cronómetro contará hacia adelante desde 00:00, como es estándar en los partidos.8
Gestión del Estado
Un objeto JavaScript simple gestionará el estado de la aplicación, manteniendo un registro del marcador actual, el tiempo de juego, el jugador seleccionado y otra información relevante.
Captura de Eventos y Empaquetado de Datos
La interfaz de usuario debe ser una herramienta de captura de eventos optimizada, no un formulario de entrada de datos tradicional. Los formularios web estándar son demasiado lentos para la anotación en vivo.9 Por lo tanto, la arquitectura de JavaScript debe priorizar la velocidad y minimizar la fricción del usuario.
El flujo de trabajo será "seleccionar jugador, luego hacer clic en la acción". Esto minimiza los clics y la carga cognitiva.
Selección de Jugador: Se añadirá un addEventListener a los contenedores de las listas de jugadores. Al hacer clic en un jugador, se le asignará una clase active y su ID se almacenará en la variable de estado.
Captura de Acción: Se utilizará la delegación de eventos, adjuntando un único addEventListener al #action-panel. Esto es más eficiente que añadir un listener a cada botón.
Empaquetado de Datos: Cuando se hace clic en un botón de acción, el manejador de eventos:
Lee los atributos data-* del botón para obtener el tipo_evento y si requiere un resultado.
Obtiene el id_jugador del estado de la aplicación.
Obtiene el tiempo_juego actual del módulo del cronómetro.
Si se requiere un resultado, muestra un pequeño modal o botones contextuales (p. ej., "Gol", "Parada", "Fuera") para que el usuario seleccione el desenlace.
Ensambla toda esta información en un único objeto JSON, listo para ser enviado al backend.
Este proceso de interceptar una acción del usuario (como un clic en un botón de tipo submit), prevenir el comportamiento por defecto del navegador (recargar la página) y ejecutar una lógica personalizada es una técnica fundamental en el desarrollo web moderno.10
Sección 3: La Sala de Máquinas — Arquitectura del Backend en Python
En esta sección, se tomarán las decisiones tecnológicas clave para el lado del servidor, se configurará el entorno de desarrollo y se diseñará la API que funcionará como el cerebro del sistema.
3.1. Elección de la Herramienta Adecuada: Flask vs. FastAPI
La elección del framework web de Python es crucial. Los dos principales contendientes son Flask y FastAPI.11
Flask: Es un micro-framework conocido por su simplicidad, flexibilidad y una gran comunidad, lo que lo hace ideal para principiantes y para la creación de prototipos.12
FastAPI: Es un framework moderno de alto rendimiento que destaca por su soporte asíncrono, validación de datos automática a través de Pydantic y generación de documentación de API interactiva.11
Aunque FastAPI ofrece ventajas técnicas como un rendimiento superior y soporte asíncrono, estas características son excesivas para una aplicación local con un solo usuario que no tiene una alta carga de concurrencia ni operaciones de E/S intensivas.12 El objetivo principal de este proyecto es el aprendizaje. La naturaleza "no opinionada" de Flask obliga al desarrollador a ser más explícito en el manejo de solicitudes y datos, lo cual es una experiencia de aprendizaje invaluable. La vasta comunidad y la abundancia de tutoriales de Flask también proporcionan una red de seguridad más sólida para un desarrollador que se inicia en el backend.11 Por lo tanto, Flask es la opción pedagógica superior para este proyecto, ya que se alinea mejor con los objetivos educativos del usuario sin comprometer los requisitos funcionales.

Sección 4: Persistencia de Datos Local — De Archivos Simples a una Base de Datos Estructurada
Esta sección aborda cómo guardar los datos del partido. Se compararán las dos opciones más prácticas para el almacenamiento local y se proporcionará una guía de implementación completa para la solución recomendada.
4.1. La Elección: Archivo JSON Simple vs. Base de Datos SQLite Robusta
Archivos JSON: La forma más sencilla de empezar. Python incluye la biblioteca json para leer y escribir estos archivos con facilidad.21 Un archivo JSON podría almacenar el registro de eventos de un solo partido. Sin embargo, realizar consultas complejas, como agregar las estadísticas de un jugador a lo largo de varios partidos, requeriría leer y procesar múltiples archivos, lo cual es ineficiente y propenso a errores.23
Base de Datos SQLite: Es un motor de base de datos SQL completo, sin servidor y basado en un solo archivo. Está incluido en la biblioteca estándar de Python a través del módulo sqlite3.23 Permite realizar consultas potentes y estructuradas, garantiza la integridad de los datos y escala mucho mejor para análisis futuros.
El usuario ha manifestado explícitamente su intención de "agregarle más cosas más adelante". Esta es una restricción clave que guía la decisión. Mientras que un archivo JSON es un producto mínimo viable (MVP) funcional, SQLite es la elección estratégicamente correcta que se alinea con el objetivo de escalabilidad futura. Para calcular las estadísticas de un jugador en una temporada, con SQLite se ejecutaría una única y eficiente consulta SQL. Con archivos JSON, sería necesario un complejo script para iterar sobre todos los archivos de partidos. La curva de aprendizaje inicial de SQLite es ligeramente mayor, pero el beneficio a largo plazo en potencia y escalabilidad es inmenso y aborda directamente un requisito central del usuario.

Sección 5: El Protocolo de Comunicación — Conectando Frontend y Backend
Esta sección crucial une el navegador con el servidor, detallando el flujo completo de un evento desde su captura en el frontend hasta su almacenamiento en la base de datos del backend.
5.1. Envío de Datos desde JavaScript con la API Fetch
El código del lado del cliente utilizará la API Fetch para enviar los datos del evento capturado. Fetch es la interfaz moderna de JavaScript para realizar solicitudes de red.31
Se construirá una solicitud fetch al endpoint /api/event.
El método de la solicitud será POST.
Se establecerán las cabeceras (headers) a {'Content-Type': 'application/json'} para indicar al servidor que se está enviando un cuerpo en formato JSON.33
El cuerpo (body) de la solicitud contendrá el objeto de evento de JavaScript, convertido a una cadena JSON mediante JSON.stringify().33
JavaScript
// Ejemplo de función para enviar un eventoasync function sendEventToServer(eventObject) {    try {        const response = await fetch('/api/event', {            method: 'POST',            headers: {                'Content-Type': 'application/json',            },            body: JSON.stringify(eventObject),        });        if (!response.ok) {            throw new Error(`Error del servidor: ${response.status}`);        }        const result = await response.json();        console.log('Evento guardado con éxito:', result);    } catch (error) {        console.error('Error al enviar el evento:', error);    }}

5.3. El Contrato de Datos: Una Única Fuente de Verdad
La estructura del objeto JSON intercambiado entre el frontend y el backend actúa como un "contrato de datos" crítico. Definirlo explícitamente es clave para una integración exitosa. Un fallo común en el desarrollo full-stack es una discrepancia en la estructura de datos esperada (p. ej., el frontend envía playerId mientras que el backend espera player_id).
Para evitar esto, se debe tratar la estructura JSON como un acuerdo formal. Este informe define explícitamente dicho contrato, derivado del modelo de datos:
JSON
{    "id_partido": 1,    "id_jugador": 12,    "tipo_evento": "LANZAMIENTO_6M",    "resultado": "GOL",    "tiempo_juego": "12:34"}
Al mostrar esta estructura exacta siendo creada en la llamada fetch de JavaScript y luego siendo accedida clave por clave en la vista de Flask en Python, el proceso de integración se vuelve transparente y se desmitifica la comunicación entre las dos mitades de la aplicación.
